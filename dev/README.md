# hoa-admin — local DEV environment

A local copy of the admin console for testing UI/UX changes **without touching
production**. Same code, same connection points (Supabase REST API, OpenAI,
Google Drive source verification), but the database is a **local Supabase
stack in Docker**, seeded with a copy of production data.

```
dev/
├── dev.sh                       one entry point: up / seed / run / reset / status / down
├── seed_from_prod.py            clones prod → local through the API (prod is read-only)
├── supabase/config.toml         local stack config (project "hoa-admin-dev", Postgres 15)
├── supabase/migrations/…_schema.sql   exact copy of the production schema
├── .env.dev                     generated by `dev.sh up` — gitignored
└── .env.dev.example             shape of .env.dev
```

## Prerequisites (one-time)

- Docker Desktop, running
- Supabase CLI: `brew install supabase/tap/supabase`
- The workspace venv (`/Users/thomasmasters/Projects/.venv`) — the same one the tests use

## Daily use

```bash
cd hoa-backend/dev
./dev.sh up      # first run pulls images (~2 GB) and applies the schema; later runs are seconds
./dev.sh seed    # copy production data into the local stack (only needed once, or after reset)
./dev.sh run     # http://localhost:5052 — DEV badge in the sidebar, templates auto-reload
```

Sign in as any copied account **or** one of the dev accounts, all with password
`devpass123`:

| username | role |
|---|---|
| `dev-superuser` | superuser — approvals, users, tags, audit |
| `dev-board` | board — pending history, resident questions, close flags |
| `dev-member` | member — the committee view |

Edit any template or `admin_app.py`, save, reload the page. Flask's reloader
restarts on Python changes; Jinja auto-reload picks up template edits.

Other commands:

```bash
./dev.sh reset   # drop everything, re-apply the schema, re-seed from prod
./dev.sh status  # local URLs + keys (Studio: http://127.0.0.1:54323)
./dev.sh down    # stop containers (the local database persists in a Docker volume)
```

## What "same connection points" means here

| Connection | Production | DEV |
|---|---|---|
| Supabase (PostgREST + RPC `match_clauses`) | `xzqmunxbmoiuinyampsl.supabase.co` | `http://127.0.0.1:54321` — identical API, identical schema |
| OpenAI (Search page, embeddings) | real key | the same real key, copied from `../.env` — real calls, real cost |
| Google Drive PDF verification | real | real (outbound only) |
| Flask sessions / bcrypt / roles | same code | same code |

Nothing in DEV writes to production. `seed_from_prod.py` opens production
read-only and refuses to run if the local URL isn't localhost; `dev.sh run`
and `admin_app.py` (with `HOA_ENV=dev`) refuse to start against a non-local
Supabase URL.

## How it differs from production (by design)

- **Passwords.** Production hashes are never copied. Every copied account gets
  the dev password; three `dev-*` accounts are added.
- **`HOA_ENV=dev`** turns on: the DEV badge (sidebar + login page + browser
  title), Flask debug/reloader, and the localhost guard. Unset in production.
- Port **5052** (production-style local runs stay on 5051), bound to 127.0.0.1.
- Realtime, Storage, Edge Functions, Analytics and the mail catcher are
  disabled in the local stack — the console uses none of them.
- Postgres 15 with pgvector 0.8, matching production. Row Level Security is
  enabled with no policies, matching production; the service-role key bypasses it.

## Troubleshooting

- **`supabase start` hangs or fails** — Docker Desktop isn't running, or ports
  54321-54324 are in use (`lsof -nP -iTCP:54321 -sTCP:LISTEN`). Change ports in
  `supabase/config.toml` and re-run `./dev.sh up` (it regenerates `.env.dev`).
- **"Local tables already contain data"** — `seed_from_prod.py` refuses to
  double-seed. Use `./dev.sh reset`, or `./dev.sh seed --wipe`.
- **Login says invalid password** — the dev password is `devpass123`; the
  copied accounts do not use their production passwords.
- **Schema drift** — if production gains a column/table, add a new file under
  `supabase/migrations/` (timestamp-prefixed) mirroring the `sql/` migration
  you ran in production, then `./dev.sh reset`.
