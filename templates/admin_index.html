Help & Reference

Browse & Filters

Filter clauses by keyword (searches clause_id, citation, document, plain summary, and full clause text), document, or tag. Results are paginated at 25 per page. Active filters persist across page turns.

Only clauses with status = approved are visible to residents via the Carrd chatbot. All statuses are visible here in the admin console. Approved changes reach residents automatically within the corpus cache window (~1 hour) — no redeploy needed.

Clause cards show a ⏳ Pending Approval badge when a change is queued but not yet approved. The live clause text remains unchanged until the pending change is approved.

Cards with an orange left border have a stale embedding — the clause text has changed since the embedding was last generated (see Embeddings below for what that does and doesn't affect).

Clause Pages

Every clause has its own page at /admin/clauses/<CLAUSE_ID> — click any clause ID badge or link anywhere in the console (browse cards, audit log, pending changes, flags, resident questions) to open it. The page shows the full clause, an edit form, its pending and decided changes with field diffs, any revision flags, and its change history — everything about one clause in one place.

Approval Workflow

Every clause change — add, edit, or delete — must be approved by a second admin before it takes effect in search results.

  • Submit for Approval — queues the change in Pending. The live clause is unchanged until approved.
  • ⚠ Self-approve (superusers only) — applies the change immediately, bypassing the two-person rule. Use only when no other admin is available. A warning is recorded in the audit log.
  • Deletions always require a second superuser to approve — self-approve is disabled for deletes.
  • The Pending nav item shows an orange badge when items are waiting. The page shows a field-by-field old → new diff for each change.
  • The Pending page's History tab (visible to board and up) lists every decided change with who approved or rejected it, when, and the rejection reason — the permanent governance record.
  • My Submissions (in the sidebar, all users) shows your own submitted changes, their status, and the reviewer's rejection reason if declined.

Source Verification

When a clause is submitted for approval, the system automatically downloads the linked Google Drive PDF and checks whether the clause text appears on the stated page using fuzzy text matching.

  • ✅ Verified — strong match found (≥ 80% similarity)
  • ⚠️ Partial — partial match found (50–79%)
  • ❌ Not Found — text not found on that page (< 50%)
  • ⏭ Skipped — PDF could not be accessed, or clause text was missing

Verification is advisory only — it informs the approver but never blocks submission or approval.

Three source fields are required on every clause: Citation, Page, and a Google Drive link (https://drive.google.com/…).

Add Clause

Manually add a single clause. Citation, page, and a Google Drive source link are required. At least one of clause_text or plain_summary must be provided.

The embedding is not generated automatically on add — use Regenerate Embedding on the approved clause afterward so it appears in semantic search results.

Precedence Level encodes document authority: lower numbers = higher authority (1 = Texas Property Code, 2 = CC&Rs, … 9 = Builders Guidelines). The resident bot sorts clauses by precedence when building answers, and ties in relevance scoring break toward the more authoritative clause. Match the document family's standard level — don't invent new values.

Import CSV — Add

Superusers only. Bulk-inserts clauses from a .csv file. Download the blank template for the correct column layout. Each row must include citation, page, and a Google Drive link — rows missing any of these are skipped. CSV imports go live immediately (no approval step). Column rules:

  • At least one of clause_text or plain_summary must be non-empty per row
  • page and precedence_level must be whole numbers if provided
  • tags — comma-separated, e.g. fence, arc
  • match_source defaults to CSV Import if omitted
  • Columns not in the template are rejected; valid rows are inserted even if others in the same file fail

All imported clauses start with stale embeddings and will not appear in semantic search until regenerated.

{% endif %} {% if is_superuser %}

Import CSV — Delete

Superusers only. Permanently deletes every Supabase row whose clause_id matches a value in the uploaded file. There is no undo. Bulk CSV deletes go live immediately — no approval step, no second-person requirement. The CSV must contain a clause_id column; all other columns are ignored.

{% endif %}

Embeddings

Each clause stores an embedding — a numeric vector used only by the legacy admin vector search (e.g. finding near-duplicate clauses in the Search Test's collapsed section). The resident chatbot does not use embeddings — it uses keyword/tag relevance scoring over the full corpus — so embedding status never affects resident answers.

  • Editing clause_text marks the embedding stale when the edit is approved and applied. Tag-only or summary-only edits don't require regeneration.
  • Stale clauses are excluded from the legacy vector search until regenerated.
  • Use Regenerate Embedding on any clause to call OpenAI and refresh it. No approval required — takes effect immediately.
  • Model in use: {{ embedding_model }}

Tag Management

Superusers only, via Tags in the sidebar. Lists every distinct tag with its clause count. Renames apply across all clauses immediately (no two-person approval) and are audit-logged per clause; renaming into an existing tag merges them; Delete removes a tag everywhere. New names are always UPPERCASE — the corpus convention. Mixed-case tags are badged for cleanup.

Tags matter: the resident bot's relevance scoring weights tag matches 3× over incidental text matches, so clean tags directly improve answers. Tag changes reach residents within the corpus cache window (~1 hour) and never require embedding regeneration.

{% endif %}

Export CSV

The Export CSV panel downloads the clause database honoring your current browse filters (keyword, tag, document, stale). Columns match the import template plus id and status, so export → edit → re-import round-trips. Use it for backups and offline committee review packets. Embeddings are excluded.

Search Test

The primary result is a Prefilter Preview: it runs the exact scoring loop the resident bot uses (filter_relevant_clauses) and shows which clauses would be selected for a question, with per-clause scores — or whether the full-corpus FALLBACK would fire. GPT is never called, so this costs nothing; the full end-to-end test (which does call GPT) is the Search page.

A collapsed Legacy search section still offers the old vector + keyword searches. The resident bot uses neither — they remain only as admin tools (e.g. finding near-duplicate clauses).

Each legacy result row includes a Flag button — use it to flag a specific clause for revision directly from search results without leaving this page.

Admin Search

Available via Search in the sidebar. Runs a full GPT-powered Q&A query through the same pipeline as the resident-facing Carrd chatbot (relevance prefilter → full-corpus GPT prompt → cited answer) — but with flagging capability built in. This calls GPT, so it costs tokens; for a free corpus-selection preview use the Search Test panel instead. Admin searches are not logged to the resident question log.

  • The GPT answer is displayed at the top, followed by the cited clause cards that informed it.
  • Each cited clause card has a Flag for Revision button to flag that specific clause.
  • Flag this topic at the top of results captures the entire question, GPT answer, and all cited clause IDs as a single topic-level flag — useful when the concern is about a policy area rather than one specific clause.

Resident Questions

Board and up, via Resident Questions in the sidebar. Every question residents ask the Carrd chatbot is logged automatically — question, answer, cited clauses (linked to their clause pages), and prefilter telemetry. Admin-console searches are deliberately excluded.

  • FALLBACK rows are the gold: the relevance prefilter found too little signal, meaning the governing documents probably don't cover that topic clearly. Filter to "Fallback only" to build the committee's gap list.
  • "No citations" filters to answers GPT couldn't ground in any clause.
  • Whimsy questions ("who made you?") are logged but hidden by default — toggle "Include whimsy" to see them.
  • Privacy: no IP or identity is stored; retention is 24 months.
{% endif %}

Revision Flags

Available via Revision Flags in the sidebar. A deliberation tool for the CCR revision committee — flags do not change any clause data. The existing edit and approval workflow is downstream of this process.

  • Clause flag — marks a specific clause for revision discussion. Triggered from the clause browse list, the Search Test results, or the Admin Search cited clause cards. The 🏳 Flag button on a clause card turns to 🚩 Flagged once an open flag exists.
  • Topic flag — captures a full Q&A result (question, GPT answer, and cited clause IDs) when the concern spans multiple clauses or a broader policy area.
  • Any logged-in user can create flags and add comments. Closing a flag requires the board role or higher.
  • Cited clause IDs on a flag link straight to their clause pages, and each clause page lists the flags that reference it.
  • Statuses: Open → In Review → closed as No Change, Changed, or Deferred.
  • The flag detail page shows the full clause or topic snapshot, original flag notes, a threaded comment history, and status management. Comments are permanent — they cannot be edited or deleted.
  • The Revision Flags nav item shows an orange badge when open flags exist.

Audit Log

Every action is recorded — clause adds, edits, deletes, approvals, rejections, embedding regenerations, tag renames/deletes, role changes, user changes, password resets, and CSV imports. Accessible via Audit Log in the sidebar (superusers only). Filter by user, action type, or date range. Clause IDs link to their clause pages. All timestamps are displayed in UTC.

Roles & User Management

Accessible via the Users link in the sidebar. Three hierarchical roles — each includes everything below it, and each exists for one purpose:

  • Member — the Document Revision Committee. Community volunteers (plus a board member and an ARC member) revising the governing documents: review clauses, flag and discuss what should change, propose changes, track them under My Submissions. Members never approve changes.
  • Board — the accuracy reviewer. Reviews the tool itself for accuracy: watches Resident Questions, flags and corrects database inaccuracies, closes revision flags, reads the Pending History. Cannot approve clause edits or manage users.
  • Superuser — the final approvers (the HOA president and the developer). Every change reaching residents passes a superuser's accuracy check; deletions need the second superuser. Also: user/role management, tags, imports, audit log.
  • Superusers set roles from the Users page via the role dropdown. You cannot change your own role, and the last superuser cannot be demoted.
  • Role changes and deactivations take effect on the user's next request — not at their next login.
  • You cannot deactivate or delete your own account from the admin UI.
  • Login sessions expire after 8 hours. Login and logout events are recorded in the activity log.
